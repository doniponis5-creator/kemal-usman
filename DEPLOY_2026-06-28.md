## 2. O!Dengi 503 INCIDENT — sabab va tuzatish (kelajak uchun yozib qo'yildi)

**Belgisi:** Deploy'dan keyin webhook smoke-test **503** qaytardi (oldin 403). 503 = `payment_not_configured` → online to'lov ishlamasdi.

**Haqiqiy sabab (KOD EMAS):**
- Serverda **Caddy yo'q**. `api.kemalusman.kg` **Cloudflare Tunnel** orqali → `http://localhost:8091`ga ulanadi (`/etc/cloudflared/config.yml`).
- `deploy-odengi.sh`ning step-4 restart fallback'i (`systemctl restart pocketbase` ishlamadi, chunki systemd xizmati yo'q) → tunnel ulangan **8091** nusxasini **env'siz** (`nohup ./pocketbase ...`) qayta ishga tushirgan → `ODENGI_PASSWORD` yo'qoldi → 503.
- Diagnostika tasdig'i: `127.0.0.1:8090 → 403` (parolli), `127.0.0.1:8091 → 503` (parolsiz), `PUBLIC → 503` (=8091).

**Qilingan tuzatish (2026-06-28 ~09:28):** hamma PB o'chirildi, bitta nusxa **8091**'da (tunnel porti) haqiqiy env bilan, faqat loopback'da qayta ishga tushirildi. Parol kredensial fayldan olindi. Natija: **PUBLIC webhook → 403**, GREEN_API (OTP) ham yuklandi.

**Agar PB yana o'lsa / payment yana 503 bo'lsa — vaqtinchalik tiklash buyrug'i** (systemd o'rnatilгунча):
```bash

set -a; [ -f /etc/pocketbase/env ] && . /etc/pocketbase/env 2>/dev/null; set +a
```

## 3. Hozirgi server holati — chalkashlik (KEYIN tozalanadi)

- **Watchdog/respawner bor:** `pkill`dan keyin 8090 nusxa **yana ko'tarildi** (yangi PID). Nimadir PB'ni qayta ishga tushiradi.
- **2 ta PB bitta `data.db`ni baham ko'ryapti** (`/root/parfum-backend/pb_data`) — SQLite uchun xavfli (lock/korruptsiya ehtimoli). *Eski muammo, deploy'dan oldin ham bor edi.*
- **systemd xizmati yo'q** → reboot'da PB ko'tarilmaydi (nohup).
- **`/etc/pocketbase/env` 2-qator (`ODENGI_PASSWORD`) qiymatida probel bor** → bash `source` buziladi (`KMGH...: command not found`). *systemd EnvironmentFile esa probelni to'g'ri o'qiydi — shuning uchun systemd'ga o'tish buni ham hal qiladi.*
- PB `0.0.0.0:8090/8091`ga bog'lanган (public'ga ochiq) — SECURITY_HARDENING faqat `127.0.0.1` deydi. Yangi 8091 nusxa allaqachon loopback'da.

### 4.3 — systemd xizmatini to'g'ri o'rnatish (ASOSIY — hammasini bir yo'la hal qiladi)
Bu reboot-persistence + dublikat-nusxa + env-yuklash muammosini birvarakayiga yopadi.

**Tunnel `localhost:8091`ga ulanadi → xizmat ham `127.0.0.1:8091`da bog'lansin.**

`/etc/systemd/system/pocketbase.service` (hozirgi reallikка moslangan — `/root/parfum-backend`, root):
```ini
[Unit]
Description=PocketBase backend (parfum)
After=network.target

[Service]
Type=simple
WorkingDirectory=/root/parfum-backend
ExecStart=/root/parfum-backend/pocketbase serve --http=127.0.0.1:8091
EnvironmentFile=/etc/pocketbase/env
Restart=always
RestartSec=5
LimitNOFILE=65536

[Install]
WantedBy=multi-user.target
```
> Eslatma: hozir PB `root`da ishlaydi. Xavfsizroq variant — `pocketbase` user yaratib, `pb_data`/`pb_hooks`'ni unга `chown` qilib, unit'ga `User=pocketbase` qo'shish (repodagi `deploy/pocketbase.service` namunasiga qarang — lekin u `/opt/pocketbase`ga ishora qiladi, biznikida `/root/parfum-backend`). Hardening (`ProtectHome=yes`) `/root`dan ishlaganda bloklaydi — shuning uchun yo `/opt/pocketbase`ga ko'chiriladi, yo `ProtectHome` olib tashlanadi.
